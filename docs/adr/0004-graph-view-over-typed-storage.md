# Derive a Graph View from typed storage, instead of a generic nodes/edges store

To support a family-tree visualization and (later) a chat-based model recommender, we needed the Hub's data to be an explicit, queryable graph rather than content baked into rendering code — and the user wants an actual graph diagram shown in the demo. We considered migrating everything into a generic `nodes`/`edges` store, and rejected it: storage stays as today's typed entities (Model data, per-model literature JSON, the `communityEvidence`/`mechanisticFindings`/`bayesianAnnotations` collections), plus two new typed additions — Known Variant and the Lineage/Fixes relationships (see CONTEXT.md). A **Graph View** — a `{nodes, edges}` structure assembled on demand from all of the above — is what the visualization and recommender actually consume.

**Why:** a generic graph store earns its cost when you don't yet know what relationship types you'll need. We do: every relationship this feature actually requires (Model↔Model lineage, Variant→FailureMode fixes, and cross-Model evidence via the already-shared Reference entity) fits cleanly as a typed addition to what already exists and works. Migrating everything into a generic store to hedge against *hypothetical* future relationship types would have meant rewriting working storage for no near-term payoff, and the "showcase an actual graph in the demo" requirement is satisfied just as well by deriving a view as by making the view the master copy.

**Considered options:** a generic `nodes`/`edges` store as the master data shape, with every existing relationship re-expressed as edges in it — rejected for the reason above; revisit if a future relationship type genuinely doesn't fit the typed-collection pattern.
